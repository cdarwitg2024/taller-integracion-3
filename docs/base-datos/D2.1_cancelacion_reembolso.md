## 1. Objetivo y alcance

Permitir que un **estudiante** cancele **su propio pedido** mientras todavía no
comenzó la preparación, devolviendo **automáticamente** el monto pagado a su
**Wallet** (saldo interno).

Alcance de este documento:

- Regla de negocio y estados válidos.
- Flujo de pago existente (`procesar_pago`) con el que se relaciona.
- Tablas y columnas involucradas (confirmadas contra la BD real).
- Contrato exacto que `ms-pedidos` espera de la RPC `public.cancelar_pedido`.
- Idempotencia / prevención de doble reembolso.
- Riesgos de seguridad (policies RLS) que el responsable de BD debe resolver.
- Responsabilidades por rol.

Fuera de alcance: cambios de UI (Mobile/Desktop), Orquestador, inventario/stock,
cambios en `pagos.estado`.

---

## 2. Regla de negocio

El estudiante **solamente** puede cancelar **su propio** pedido mientras se
encuentre en:

```
pendiente
```

Flujo:

```
pendiente  ──►  cancelado  ──►  reembolso automático a Wallet
```

**NO se puede cancelar** desde:

```
en_preparacion
listo
entregado
```

Notas importantes sobre estados:

- `pendiente` significa **"pedido ya pagado, pendiente de preparación"**. No es
  "pago pendiente": el cobro ya ocurrió (ver secciones 3 y 9).
- `pagado` **solamente** se tolera como **estado legacy equivalente a
  `pendiente`** para pedidos antiguos que quedaron con ese texto en la BD. Es una
  **compatibilidad de lectura**, no un destino válido.
- **NO debe volver a escribirse** `pedidos.estado = 'pagado'`. Los pedidos nuevos
  usan `pedidos.estado = 'pendiente'`.
- `cancelado` es un **estado terminal**.
- `pedidos.estado` es `VARCHAR(50)` **sin** `CHECK`/`ENUM` en la BD real, por lo
  que la base **no** impide por sí sola valores inválidos: la validación ocurre en
  la RPC y en `ms-pedidos`.

## 3. Flujo de pago existente (`procesar_pago`)

`public.procesar_pago(p_cafeteria_id BIGINT, p_items JSONB, p_franja_retiro TEXT)`
es la autoridad transaccional del pago. Realiza, en una sola transacción:

1. Valida el usuario autenticado.
2. Recalcula el total desde los **precios reales** de `productos` (no confía en
   montos del cliente).
3. Bloquea la Wallet (`FOR UPDATE`).
4. Verifica saldo suficiente.
5. Descuenta el saldo.
6. Crea el pedido.
7. Crea los detalles del pedido.
8. Registra el pago en `pagos`.
9. Registra el movimiento en `movimientos_wallet`.

Si **no hay saldo suficiente**: **NO se crea el pedido** (rollback completo).

La BD real, tras un pago exitoso, deja:

| Campo | Valor |
| --- | --- |
| `pedidos.estado` | `'pendiente'` |
| `pedidos.pago_estado` | `'pagado'` |
| `pedidos.metodo_pago` | `'wallet'` |
| `pagos.estado` | `'aprobado'` |
| `movimientos_wallet.tipo` | `'compra'` (monto **negativo**) |

> **No confundir** el **estado operacional del pedido** (`pedidos.estado`: dónde
> va el pedido en cocina/entrega) con el **estado del pago** (`pedidos.pago_estado`
> / `pagos.estado`: si el dinero se cobró). Son conceptos independientes y se
> actualizan por caminos distintos.

`procesar_pago` **no descuenta stock** (no hay integración de inventario activa).

## 5. RPC requerida

`ms-pedidos` espera que exista:

```
public.cancelar_pedido(p_pedido_id BIGINT) RETURNS JSONB
```

Requisitos de la función:

- `SECURITY DEFINER`
- `SET search_path = public`
- Debe **obtener el usuario desde la sesión/JWT** (no desde el cliente).
- **NO debe recibir `usuario_id`** desde el cliente.
- La implementación propuesta usa `public.mi_usuario_id()` (deriva de
  `auth.uid()`, retorna `BIGINT`, está versionada en
  `database/fixes/politica_logs_auditoria_por_usuario.sql`).

---

## 6. Comportamiento requerido de `cancelar_pedido`

En una **sola transacción**:

1. **Resolver usuario autenticado** (desde la sesión). Si no hay → excepción
   `sin_sesion`.
2. **Buscar y bloquear el pedido**: `SELECT ... FROM pedidos WHERE id = p_pedido_id FOR UPDATE`.
3. **Verificar propiedad**: el pedido debe pertenecer al usuario. Si no →
   `no_autorizado`.
4. **Verificar estado**:
   - Cancelable: `pendiente`.
   - Compatibilidad legacy (lectura): `pagado`.
   - Ya cancelado → `ya_cancelado`.
   - No cancelable (`en_preparacion`, `listo`, `entregado`, u otro) → `no_cancelable`.
5. **Obtener el monto** desde `pedidos.total`. **NO recalcular** desde
   `productos.precio`.
6. **Validar conversión a `INTEGER`** (la Wallet usa `saldo_actual INTEGER`):
   - `total > 0`
   - `total` debe ser entero (`total = trunc(total)`)
   - `total <= 2147483647`
7. **Buscar y bloquear la Wallet**: `SELECT ... FROM wallets WHERE usuario_id = ... FOR UPDATE`.
   Si no existe → `sin_wallet`.
8. **Validar overflow antes de acreditar**: `saldo_actual + monto` no debe exceder
   `2147483647`; si excede → `saldo_invalido`.
9. **Acreditar el monto** a `wallets.saldo_actual`.
10. **Crear el movimiento** en `movimientos_wallet`:
    - `tipo = 'reembolso'`
    - `monto` = **POSITIVO**
    - `pedido_id` = pedido cancelado
    - `descripcion` no nula
11. **Actualizar el pedido**:
    - `estado = 'cancelado'`
    - `cancelado_en = CURRENT_TIMESTAMP`
    - **NO** tocar `pago_estado`, `pagos.estado`, stock, QR ni otros timestamps.
12. **Retornar JSON** (ver sección 8).

### Montos por tipo de movimiento

| `tipo` | Signo de `monto` | Origen |
| --- | --- | --- |
| `recarga` | positivo | recarga de saldo |
| `compra` | **negativo** | `procesar_pago` |
| `reembolso` | **positivo** | `cancelar_pedido` |

---

## 7. Idempotencia / prevención de doble reembolso

Debe impedirse:

```
cancelar dos veces  →  recibir dos reembolsos   (PROHIBIDO)
```

Mecanismo requerido — **orden de locks**:

```
PEDIDO  FOR UPDATE
      ↓
WALLET  FOR UPDATE
```

- Toda la operación es una transacción. Una segunda solicitud **concurrente**
  espera el lock del pedido y, al continuar, encuentra `estado = 'cancelado'` y
  **NO vuelve a acreditar dinero** (responde `ya_cancelado`).
- El orden de locks (`pedido` → `wallet`) evita ciclos de deadlock frente a
  `procesar_pago` (que solo bloquea `wallet`).
- La segunda cancelación **no** debe insertar otro movimiento ni sumar saldo.

---

## 8. Contrato de respuesta esperado por `ms-pedidos`

### Éxito

```json
{
  "ok": true,
  "pedido_id": 123,
  "estado": "cancelado",
  "monto_reembolsado": 3500,
  "saldo_nuevo": 8500
}
```

### Motivos (`ok: false`, `motivo`)

| `motivo` | Significado | HTTP esperado en `ms-pedidos` |
| --- | --- | --- |
| `pedido_no_encontrado` | No existe el pedido | 404 |
| `no_autorizado` | El pedido no es del usuario | 403 |
| `ya_cancelado` | Ya estaba cancelado (sin reembolso nuevo) | 409 |
| `no_cancelable` | Estado no permite cancelar | 409 |
| `monto_invalido` | `total` nulo o `<= 0` | 422 |
| `monto_no_entero` | `total` no entero o fuera de rango `INTEGER` | 422 |
| `saldo_invalido` | Overflow al acreditar | 422 |
| `sin_wallet` | El usuario no tiene Wallet | 503 |

### Sin sesión

La **ausencia de sesión** puede producir `sin_sesion` (se recomienda
`RAISE EXCEPTION` con SQLSTATE `42501`). `ms-pedidos` lo traduce a **403**.

> El mapeo a HTTP del lado Node ya está implementado. Si el responsable de BD
> cambia estos `motivo`, **debe comunicarlo** para ajustar `ms-pedidos`.

## 9. Pagos

**NO es necesario cambiar** `pagos.estado = 'aprobado'` al cancelar.

- `'aprobado'` representa que el **cobro original ocurrió correctamente**; sigue
  siendo un hecho histórico válido aunque el pedido se cancele.
- El reembolso se registra mediante `movimientos_wallet.tipo = 'reembolso'`
  (monto positivo).
- Esto mantiene el historial coherente del ledger:

```
compra      →  monto negativo
reembolso   →  monto positivo
```

## 10. Policies / seguridad — problema REAL encontrado

### 10.1 `pedidos_update_cancelar_own` (bypass a eliminar)

Actualmente existe una policy que permite al **propietario** hacer `UPDATE`
directo:

```
pendiente/pagado → cancelado
```

**sin ejecutar el reembolso**. Definición real obtenida de Supabase:

```sql
-- USING:
usuario_id = mi_usuario_id()
AND lower(estado) IN ('pendiente', 'pagado')

-- WITH CHECK:
usuario_id = mi_usuario_id()
AND lower(estado) = 'cancelado'
```

El responsable de BD debe **revisar/eliminar** esta vía para que la cancelación
del estudiante pase **obligatoriamente** por `cancelar_pedido`. En el SQL de
referencia se incluye (comentado, no aplicado):

```sql
DROP POLICY IF EXISTS "pedidos_update_cancelar_own" ON public.pedidos;
```

### 10.2 `pedidos_update_staff` (riesgo separado)

Definición real obtenida de Supabase:

```sql
-- USING:
cafeteria_id IN (SELECT mis_cafeterias_ids())

-- WITH CHECK:
cafeteria_id IN (SELECT mis_cafeterias_ids())
```

Esta policy **NO restringe `estado`**. Por lo tanto existe el riesgo de que un
**staff autenticado** haga `UPDATE` directo:

```
estado = 'cancelado'
```

**sin reembolso**, saltándose el flujo de negocio.

> **Gestionar como riesgo separado.** El responsable de BD debe decidir/aplicar
> la policy definitiva. Recomendación: el staff debe conservar las operaciones
> normales que necesita el KDS (`pendiente → en_preparacion → listo → entregado`),
> pero **no debe poder producir directamente una fila con `estado = 'cancelado'`**
> saltándose `cancelar_pedido`.

> **Deuda técnica relacionada:** `mis_cafeterias_ids()` es referenciada por esta
> policy pero **no está versionada** en el repositorio (ver sección 13).

## 11. RLS (Row Level Security)

RLS está **habilitado** (no forzado) en:

```
pedidos
wallets
movimientos_wallet
pagos
```

Policies actuales conocidas:

| Tabla | Policy | Uso |
| --- | --- | --- |
| `movimientos_wallet` | `movimientos_wallet_select_own` | SELECT propios |
| `pagos` | `pagos_select_own_or_staff` | SELECT propio o staff |
| `pedidos` | `pedidos_insert_own` | INSERT propio |
| `pedidos` | `pedidos_select_own_or_staff` | SELECT propio o staff |
| `pedidos` | `pedidos_update_cancelar_own` | **bypass a eliminar** (sección 10.1) |
| `pedidos` | `pedidos_update_staff` | staff (riesgo, sección 10.2) |
| `wallets` | `wallets_insert_own`, `wallets_select_own` | INSERT/SELECT propios |

**Importante:**

- `authenticated` **NO** tiene policy `UPDATE` sobre `wallets`.
- `authenticated` **NO** tiene policy `INSERT` sobre `movimientos_wallet`.

Por eso el reembolso **debe** realizarse mediante una operación segura de
servidor/RPC (`SECURITY DEFINER`), y **no** mediante modificaciones directas del
cliente.

## 13. `procesar_pago` / `rpc_qr.sql` — desincronización y deuda técnica

Se encontró una **desincronización** entre la definición desplegada de
`procesar_pago` y el archivo versionado en el repositorio.

La **BD real** de `procesar_pago` utiliza:

```
v_wallet_id BIGINT
get_current_user_id()
pedidos.estado       = 'pendiente'
pedidos.pago_estado  = 'pagado'
pagos.estado         = 'aprobado'
```

El repositorio fue **reconciliado** (etapa D.2.1-D) para reflejar la función
desplegada:

- `v_wallet_id` pasó de `UUID` a `BIGINT`.
- El resolver pasó de `mi_usuario_id()` a `get_current_user_id()`.
- La escritura de `pago_estado` y del JSON pasó de `'aprobado'` a `'pagado'`.
- `pagos.estado = 'aprobado'` se mantiene.

> **Deuda técnica:** `get_current_user_id()` **existe en Supabase pero su
> definición NO está versionada** en el repositorio. Lo mismo ocurre con
> `mis_cafeterias_ids()` (usada por `pedidos_update_staff`). El responsable de BD
> debería **versionar** ambas funciones (definición en SQL controlado) para evitar
> dependencias ocultas. En esta etapa **NO** se crean ni modifican.

Observación documental adicional (no corregida aquí): el archivo de documentación
`docs/puesta_en_marcha_flujo_pedidos.md` referencia
`database/fixes/crear_rpc_pagos.sql`, que **no existe** en el repositorio.

## 14. Responsabilidades

### `ms-pedidos` / backend

- **Consume** `cancelar_pedido` (ya implementado).
- **Envía** el JWT del estudiante (nunca `service_role` para simular identidad).
- **Interpreta** la respuesta por `ok` + `motivo` y la mapea a HTTP.
- **Mantiene** la máquina de estados canónica para las transiciones no-cancelación.
- **Nunca** hace `UPDATE` directo a `'cancelado'`.

### Responsable de Base de Datos

- **Revisar** el SQL propuesto (`rpc_cancelar_pedido.sql`).
- **Implementar/versionar** la RPC definitiva `public.cancelar_pedido`.
- **Revisar las policies**, en especial:
  - eliminar/reemplazar `pedidos_update_cancelar_own`;
  - acotar `pedidos_update_staff` para que no permita `estado='cancelado'`.
- **Aplicar** los cambios a Supabase (cuando corresponda).
- **Validar RLS** (que `authenticated` no pueda alterar saldos ni insertar
  movimientos directamente).
- **Versionar** `get_current_user_id()` y `mis_cafeterias_ids()`.
- **Comunicar** cualquier cambio de contrato (campos de respuesta, `motivo`,
  firma de la función).

### Mobile / Desktop

- **Consumir** el flujo aprobado una vez implementado.
- **NO** realizar `UPDATE` directo a `'cancelado'`.
- (Estado actual: el móvil no expone cancelación; el escritorio todavía tiene un
  camino de cancelación directa que **deberá migrarse** a la RPC en su etapa.)
